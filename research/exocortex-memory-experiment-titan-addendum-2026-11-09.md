## Журнал изменений (редакция 2026-11-09b)

Первая версия этого файла — коммит `89637f46453662e41c388bf4bb9ea9f554bdb3f8`. Исправления по рецензии:

## Варианты A–E (без изменений)

- **A — NO HISTORY:** контроль без истории.
- **B — TEXT HISTORY:** та же информация обычным текстом.
- **C — STRUCTURED MEMORY:** структурированная память.
- **D — CHANGED CIRCUMSTANCES:** похожий случай с изменёнными условиями (проверка против ложного переноса).
- **E — CORRECTED BELIEF:** устаревший вывод плюс исправление.

Обязательные контроли (без изменений): одинаковые задания; одинаковый объём контекста; одинаковые модели и параметры; независимые повторы; негативные контроли; provenance; frozen artifacts.

## Часть I. Эксперимент о формате памяти (A–E)

Это исследование о том, как формат переданной памяти влияет на поведение модели. Оно не обязано идти через Titan и не проверяет Crystal само по себе.

### 1. Допустимые пути запуска

Прогон A–E валиден, если для каждого ответа сохранены:

- точное тело окончательного запроса к провайдеру: полный список `messages` (роли и полные тексты), без последующего редактирования;
- модель, параметры вызова и идентификатор прогона;
- зафиксированные артефакты (коммиты кода и значения настроек, если они участвовали в сборке).

Отсюда два допустимых пути.

1. **Прямой вызов провайдера** (как в пилоте e01–e12), если скрипт сам сохраняет точный payload. Такой прогон даёт provenance отправки: видно, что именно ушло в модель. Он проверяет формат памяти и поведение модели на этом payload. Он не проверяет сборку контекста Titan и не проверяет отбор оснований Crystal.
2. **Вызов через Titan** (`main` на коммите `6b45854`), если сохраняется и `context_report` API, и отдельный журнал точного окончательного запроса. Такой прогон проверяет ещё и то, как Titan собирает системную инструкцию, историю и записи памяти. Это **новые экспериментальные условия**. Их нельзя сливать с пилотом e01–e12 и с любыми прямыми вызовами: другая сборка промпта, другие пределы, другая инструкция. Прежние результаты сохраняются отдельно и не переписываются.

Если цель серии — именно формат памяти, оба пути законны при сохранённом payload. Если цель — сборка контекста Velantrim-рантайма, нужен путь через Titan. Если цель — ограничения Crystal (объект, время, допущенные и исключённые основания), одного Titan недостаточно: см. часть II.

### 2. Что возвращает `context_report` на Titan `6b45854`

Поле API `context_report` — это `ContextReport.to_dict()`. В нём есть:

- `provider`, `message_char_limit`, `message_char_limit_setting`;
- `token_count` (сейчас `not_computed`) и `token_count_note`;
- `memory_records_total`, `memory_records_sent`;
- `memory_records_omitted`: список `{position, fact_id}` (без текста записи);
- `history_turns_total`, `history_turns_sent`;
- `limits_applied` и `applied` (какие настройки что затронули).

В JSON отчёта **нет**:

- `sent_facts`;
- `sent_fact_positions`.

Метод `sent_facts(facts)` внутренний: он возвращает записи из поданного списка по внутреннему полю `sent_fact_positions`. Чтобы им воспользоваться, нужен тот же список фактов, который получили `_build_system_prompt`. Сам API этот список не отдаёт.

Следствия:

- отчёт API полезен как сводка количеств, пропусков по `fact_id` и применённых пределов;
- он **не заменяет** журнал точного окончательного запроса;
- одних идентификаторов и количеств недостаточно, чтобы доказать, какой текст, объект, время и источник ушли в модель.

Поэтому рядом с каждым ответом Titan сохраняются:

1. сырой `context_report` в том виде, как его вернул API, без правок задним числом;
2. отдельный журнал окончательных `messages` (полные тела).

Карту ссылок `[ev_N]` (черновик [PR #515](https://github.com/velantrian/Velantrim-ExoCortex-Titan/pull/515), не в `main`) нельзя строить из API-отчёта: в нём нет `sent_facts`. Её нужно строить из реально отправленных записей — через внутренний `sent_facts()` при наличии того же списка фактов либо разбором журнала `messages`.

### 3. Эндпоинты Titan, если выбран путь через Titan

- можно: `/chat` и `/query` — оба возвращают `context_report`;
- нельзя опираться на `/query/roles`: у него нет `context_report`;
- потоковый `/chat/stream` допускается только если сохраняются событие `context` и финальный `context_report`, **плюс** журнал точных `messages`. По умолчанию — нестримовый `/chat`.

`/chat` на коммите `6b45854` **не вызывает Crystal**. У Titan собственный поиск (`pipeline_run` / память Titan) и автосохранение. Записи, которые попадут в промпт без явного моста, — это память Titan, а не основания Crystal.

### 4. Frozen artifacts для серии A–E

Для каждой серии фиксируются путь запуска (прямой вызов или Titan) и:

- если Titan: коммит `6b45854f57ca90516b86b2c48b284c88857bc2c2`;
- модель и параметры вызова;
- если Titan участвует в сборке, значения всех пяти настроек контекста.

| Настройка | По умолчанию в Titan | Для A–E через Titan |
|---|---|---|
| `DEEPSEEK_MESSAGE_CHAR_LIMIT` | пусто (предела нет) | пусто, зафиксировать явно |
| `CONSOLE_PREVIOUS_SUMMARY_MAX_CHARS` | пусто (сводка целиком) | пусто, зафиксировать явно |
| `CONSOLE_HISTORY_TURN_MAX_CHARS` | пусто (реплика целиком) | пусто, зафиксировать явно |
| `LLM_CHAT_HISTORY_MAX_TURNS` | 20 | `off` или одно значение для всех вариантов |
| `CONSOLE_BLOCK_MEMORY_MAX_ITEMS` | 40 | `off` или одно значение для всех вариантов |

Пределы 20 реплик и 40 заметок нужно либо явно выключить (`off`), либо зафиксировать одинаково для всех вариантов. Иначе контроль «объём контекста» не соблюдается.

### 5. Независимые повторы

У повторов одного варианта должны совпадать сохранённые окончательные тела запросов (или явно вычисленный из них список переданных записей, включая текст). Расхождение означает разные условия. Такой повтор помечается и не объединяется с остальными без разбора.

Сравнивать только `memory_records_sent` или набор `fact_id` из `memory_records_omitted` недостаточно: отчёт не содержит тексты отправленных записей.

Что сохранённый payload даёт по вариантам:

- **A:** видно, что в запросе нет записей памяти и истории (негативный контроль).
- **B:** видно, сколько реплик реально ушло и сработали ли пределы истории.
- **C:** видно текст записей, которые ушли в промпт. Это позволяет отличить «модель не использовала запись» от «запись не дошла», если сравнивать поведение с журналом `messages`.
- **D:** видно, было ли изменённое условие в запросе. Тогда ложный перенос — поведение модели, а не потеря контекста при сборке.
- **E:** видно, ушла ли в запрос исправленная запись и ушла ли рядом устаревшая.

Через один лишь API-`context_report` пункты C–E по тексту записей не закрываются.

### 6. Отказ `llm_context_limit`

Отказ `llm_context_limit` (HTTP 413 на `/chat`, `[LLM error: llm_context_limit …]` на `/query`) — **честный исход и отдельный результат**, а не ошибка модели. Он учитывается отдельной категорией, без подмены офлайн-ответом и без повтора с урезанным контекстом.

Переполнение контекста на стороне провайдера (`LlmContextOverflowError`) учитывается так же, отдельной категорией.

### 7. Ограничения (общие для части I)

- **Отправка, а не восприятие.** Журнал `messages` и `context_report` фиксируют, что было в теле запроса. Они не доказывают, что модель это «увидела» и учла. Это проверяется только поведенчески, через варианты D и E.
- **Токены не считаются** (`token_count: not_computed`). Объём контекста сравнивается в символах и записях.
- **Лимиты провайдера.** Переполнение распознаётся эвристически, по коду ответа и известным фразам ошибок. Заранее оно не предсказывается.
- **Reader** делит документ на части (по умолчанию `chunk_chars` = 6000 символов) с отслеживанием покрытия; непрочитанный хвост помечается. Модель видит документ частями, а не целиком.
- Пилот e01–e12 остаётся отдельной серией. Новые прогоны через Titan с ним по условиям не сопоставимы.

## Часть II. Проверка связки Crystal + Titan

Это отдельная проверка, не подмена дизайна A–E. Вопрос: сохраняются ли ограничения Crystal по дороге к телу запроса, которое Titan готовит для модели?

### 8. Почему нужен явный мост

На коммите Titan `6b45854` обработчик `/chat`:

- не импортирует и не вызывает Crystal;
- при `use_memory=true` сам ищет факты через `pipeline_run` (память Titan);
- при `auto_save_memory=true` может сохранить новые записи.

Поэтому «прогнать A–E через `/chat`» само по себе не означает «в промпт попали основания Crystal». Без описанного моста это память и поиск Titan.

Минимальный мост:

1. Crystal-Test разбирает вопрос (`query_parse.parse_question`) и отбирает допустимые основания через `applicability.select` (объект и время).
2. Titan получает **ровно эти** допущенные основания как свои записи памяти.
3. Собственный поиск Titan и автосохранение в этом прогоне отключены (чтобы не подмешать чужие факты и не изменить условия).
4. Сохраняется точное тело окончательных `messages` и сверяется с основаниями Crystal: объект, время, текст, источники/provenance и исключённые записи. Одних идентификаторов и количеств из `context_report` недостаточно.
5. Неоднозначный вопрос завершается уточнением Crystal **до** вызова Titan; провайдер не вызывается.

Как подать основания в Titan без правки `main` Titan: тестовый хук/harness подменяет `pipeline_run`, чтобы он вернул заранее отобранные записи, при `use_memory=true` и `auto_save_memory=false`. Если когда-нибудь понадобится изменение кода Titan, оно делается только в отдельной песочничной ветке, не в `main` и не коммитом поверх `6b45854` без отдельной фиксации.

### 9. Что эта проверка не измеряет

- Она не отвечает, «помогает ли память модели отвечать правильнее» — это уже поведение, дизайн A–E.
- Подставной провайдер доказывает сборку запроса, а не ответ модели: вызова настоящей модели нет.
- Даже при полном совпадении `messages` с допущенными основаниями верно ограничение «отправлено ≠ воспринято».
